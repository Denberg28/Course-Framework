# Verification and release gates

Target version: **0.1.0-rc.2**. UI baseline: `2f12c31`. Evidence tier: self-reviewed, automated behavior/integration tests; simulated provider responses. Final build/commit/run evidence is attached to GitHub Actions and the release. This document does not claim live-provider or manual desktop validation.

## Acceptance criteria and required automated checks

| Gate | Acceptance/check | Expected result |
|---|---|---|
| A — source/build | `python -m compileall -q app.py desktop.py academy_theme.py course_core.py engines.py tests tools`; `git diff --check` | No syntax or whitespace errors |
| B — course behavior | `python -m unittest discover -s tests -v` | Metadata/outcomes/references excluded from modules; sample yields five modules and preserves weeks 3–4; bounded files and project schemas reject invalid input |
| C — regression/persistence | Core, native, and Streamlit tests | Accepted course and exports survive reruns; project roundtrip preserves material; replacement failure retains old file; candidates require acceptance |
| D — adapters | Provider tests and native worker tests | Correct Gemini/compatible payloads; no keys in URL/project/repr; sanitized errors; no redirect forwarding; incomplete/oversized output rejected; failures/discarded results preserve material |
| E — hardware | N/A | Software-only authoring; no physical-control path |
| F — Windows package | `python desktop.py --smoke-test`, PyInstaller build, packaged `CourseFramework.exe --smoke-test` on Windows runner | Native UI initializes; sample parses; editor contains course; packaged process exits 0; release includes ZIP and SHA256 |

Local Linux validation skips display-dependent desktop tests if no display is available. Required Windows checks run on `windows-latest` with Python 3.12. Streamlit AppTest simulates UI events; it is not a browser screenshot/layout assessment. DOCX and PDF fixtures are generated by the tests and do not require user documents. No live provider call, key, or paid test is part of CI.

## Manual checks before stable promotion

1. On Windows 10/11 x64, extract the complete package and run the EXE; verify no Python installation is required. Check 100%, 125%, and 150% display scaling; tab navigation, scrollbars, keyboard editing, window resizing, and dialogs.
2. Import a real institutional syllabus in each supported format. Verify metadata, module boundaries, hours, week ranges, objectives, and reference order. Clean up ambiguous layouts in the source editor. Confirm a scanned PDF gives the OCR message.
3. Use Google AI Studio with an account-available model. Generate a short course, inspect each outcome/topic, then revise a module. Repeat with an actual Chat Completions compatible provider and, if used, a local server. Check invalid key, unavailable model, offline network, and quota failure leave the accepted course intact.
4. Edit while a request runs; confirm candidate acceptance offers to restore the original syllabus snapshot. Discard a pending request and confirm its result is not applied. Close while busy and verify the unsaved-work prompts.
5. Save, reopen, export ZIP/Markdown/HTML; inspect JSON and ZIP for the test key; verify accepted edits remain. Simulate an unwritable destination and confirm the previous project remains readable.
6. Revert to the baseline only after exporting project material. The old app cannot reopen version-1 projects; retain Markdown copies.

## Candidate policy

Publish only after automated Linux/Windows tests and packaged smoke test pass. Keep the release a prerelease until live-provider behavior and manual desktop usability are documented as PASS. Failed required automated gates block candidate publication. Do not relabel a candidate as stable on the strength of a build or startup check alone.
